# Skull King Tavern — web client

Vite+ (`vp`), React 19, strict TypeScript. The rules for this folder are in
`docs/agent-rules/web-quality.md`.

```bash
npm ci
npm run dev        # http://localhost:5173 — proxies /api to the Rust server on 127.0.0.1:8080
                   # http://localhost:5173/?mock — online play against the mock server in the page
npm run check      # format, lint and types (vp check); `npx vp check --fix` formats
npm run test       # vp test
npm run build      # vp build
npm run fixtures:check   # the files in fixtures/engine are what the reference produces
npm run e2e        # four browsers at one table (e2e/README.md); needs Chrome, not part of `npm run test`
```

Node 22.18+, 24.11+ or 26+. Vite+ warns on other versions.

## Addresses

Every screen has an address, so a reload, a bookmark and the browser's Back and Forward land where
the player was. `src/router/addresses.ts` is the whole list.

| Address                         | What is there                                                                       |
| ------------------------------- | ----------------------------------------------------------------------------------- |
| `/`                             | GameOn's landing.                                                                   |
| `/games`                        | GameOn's Games.                                                                     |
| `/sign-up`, `/sign-in`          | Creating an account, signing in. Pages of GameOn.                                   |
| `/skull-king`                   | Skull King's home, a page of GameOn (`src/skullking`).                              |
| `/skull-king/solo`              | The solo setup, a page of its own (`src/skullking`). It asks the server for a game. |
| `/skull-king/one-screen`        | The renderer's new-game screen, for a game on one screen. It asks no server.        |
| `/skull-king/table`             | The table: an offline game, or a seat on the server. The end of a game is here.     |
| `/skull-king/score`             | The scoresheet for a game with real cards: its setup, its rounds and its end.       |
| `/skull-king/online`            | The online index. A lobby or a queue the server seated the player in is shown here. |
| `/skull-king/ranked`            | The ranked page: the one way into the ranked queue.                                 |
| `/skull-king/online/new`        | A new table of friends: private, with a code.                                       |
| `/skull-king/online/join`       | Join by code.                                                                       |
| `/skull-king/online/public`     | The public tables.                                                                  |
| `/skull-king/online/public/new` | A new public table, reached from the list.                                          |
| `/ladder`                       | The ladder.                                                                         |
| `/profile`                      | The player's own profile.                                                           |
| `/players/{id}`                 | Another player's page. `{id}` is a user id of the server's, and nothing else.       |

A path that is nobody's leads to `/skull-king`, and the address that was asked for is replaced by
it. `/api`, `/assets`, `/sw.js`, `/index.html` and `/manifest.json` are never pages.

How it behaves:

- A link is a new entry in the browser's history. The Back arrow of a page is the browser's own
  Back when the page was reached from its parent, so the history is as long as the way the player
  went. Reached any other way (a typed address), the parent takes the page's place.
- Skull King's home is the page's own. The renderer under it counts as being at its home screen.
- The legacy renderer and the address follow each other. A tap that changes its screen moves the
  address (`TavernHooks.moved`). An address that changed by itself moves the renderer
  (`showPlace`). A game that starts takes the place of the screen it was set up on, so Back from a
  table is the home screen.
- The connection follows the address: it is opened at the online addresses and given up at the
  renderer's own. GameOn's pages need none and leave the one there is alone. A device whose last
  page was seated opens online wherever it comes in.
- A seat at an online table holds `/skull-king/table`. Back does not leave it. The table's own way
  out does, and then the hub takes the table's place in the history.
- `/skull-king/table` with no game open and none saved leads to `/skull-king`. An offline game is
  saved with its first step, so a reload before anybody has bid is the home screen.
- What follows `?` in the address (`?mock`) stays on every address the page goes to.

The server gives the page for every path that is not `/api` (nginx in Compose and production, Vite
in development and preview), and the service worker gives the kept page for every navigation when
there is no network. Nothing is kept per address.

## GameOn, the frame around the game

`src/gameon/` is the frame: the landing, Games, and signing up and in, as `design/gameon.pen` draws
them (plan item W1). It is React, next to the legacy renderer and the online screens, and
`App.tsx` puts up the one the address names. `src/styles/gameon.css` has its styles: one layout for
a phone and one from 1000 px up.

- **It needs no connection.** It asks who this browser is over REST (`Online.identify`) and shows
  what it is told. On the landing and on the two forms that is `GET /me`, and a visitor without a
  session stays one. At Games the player is on their way in, so a browser without a session gets its
  guest there (`POST /auth/guest`), as it does when it connects.
- **The landing** reads the season from `GET /config` and the three at the top of the ladder from
  `GET /ladder`, which is public. With fewer than three on the ladder there is no podium.
- **Games** shows the player's seat from `Me`, the public tables that have room from
  `GET /lobbies`, and the way back into a game that is not over: a seat the server keeps
  (`Me.active`) first, else the offline game saved on this device. "Join" at a table hands the table
  to the public list, which connects and asks for the seat (`OnlineScreens`, `sit`).
- **Signing up** follows the answer to handover 064 (in 075). `register` upgrades the guest of the
  session, so a browser without one gets a guest first, and the account made of that guest takes
  the username as its display name (`PATCH /me`). A guest who was already there keeps their name.
  **Signing in** makes a connection again only when there was one.
- **Not built, because nothing is drawn or decided behind them:** "How to play", "Privacy" and
  "Imprint" in the footer, and "Suggest a game". The frames show them; the pages do not.
- A table in the public list is drawn in its host's colour (`LobbySummary.hostColor`) and called
  "{host}'s table". A row that came without the colour has no host: the server's own open tables
  are such rows. It has a plain avatar, and the name the server gave it is the whole title.
- The installed app opens at `/skull-king` (`start_url` in `public/manifest.json`), as it did when
  `/` led there.

## Skull King's home

`/skull-king` is `src/skullking/Home.tsx`, as `design/skt.pen` draws it (plan item W2). It takes the
place of the legacy renderer's home screen and starts no game itself: each way in is a link to the
screen that does.

- **Two cards, each opening a choice.** Solo and Online are buttons that open in place, one at a
  time (`aria-expanded`, and the list each one names with `aria-controls`). Solo holds "Against
  bots" (`/skull-king/solo`) and "One screen" (`/skull-king/one-screen`). Online holds "Tables"
  (`/skull-king/online`, the index with quick play, the public tables, a table of your own and the
  code) and "Ranked" (`/skull-king/ranked`). Ranked is not a card beside Online. No address changed,
  and the open card is not part of one: a page that comes back to the home has both closed.

- **The renderer is still under it.** It is "at home" there and draws nothing but its sheets: the
  greeting, the sound settings and the rules (`mountTavern`, `pageHome`). The page's controls open
  one with `data-act`, the renderer's own way, and what is behind an open sheet takes no input
  (`TavernHooks.dialog`). The greeting opens only when the page opened on the home (`greet`), and
  its button is still the tap that starts the menu theme. The renderer's own home screen is still
  in `views.ts`: the parity tests draw it next to the legacy page.
- **Who the player is** comes from `GET /me` (`Online.identify`). Looking at the home makes no
  guest and no connection. A browser without a session is a visitor: it has no chip in the bar, and
  Ranked says what it takes.
- **Jump back in** is the seat the server keeps (`Me.active`): a solo game with the server's own
  `bots`, `round` and `rounds`, or "your table" for any other game. A game saved on this device
  alone is offered when the server keeps none, and as a second line under the server's when both
  exist. A lobby or a queue has no panel.
- **Back to a seat** ("Continue", "Rejoin", "Back to your game") connects and goes to
  `/skull-king/table`; the `welcome` that follows puts the table back. The home sends no
  `solo.start`: the solo setup does.
- **Ranked** is closed while `Me.cooldownUntil` is ahead of the server's clock. Its row says so
  and leads nowhere. No time is drawn.
- **Without a connection** the home says so, Solo opens on both of its ways, and Online is dimmed
  and cannot be opened until the server answers again.
- **Your stats** and the scoresheet entry are this device's, as the renderer keeps them.

## Solo

Solo is the player alone against bots, on the server (plan item W3). `/skull-king/solo` is
`src/skullking/Solo.tsx`, as `design/skt.pen` draws it: bots 1 to 7, their skill, the scoring, the
rounds and the advanced rules. There is no pace to choose, because a solo table has no clock.

- **"Start"** connects, which gives a browser without a session its guest, and sends `solo.start`
  with `maxPlayers` as the bots plus the player and `pace` as `standard` (`Online.startSolo`). The
  table arrives as state and takes the setup's place in the history.
- **What the server refuses starts nothing.** `VALIDATION` is said under the button in the
  server's words. `ALREADY_SEATED`, or a `welcome` that already has a seat, leads to
  `/skull-king/table`, where the connection gives the seat back.
- **The device takes over only when the server cannot be asked:** no answer in the time an action
  gets (`DISPATCH_TIMEOUT_MS`, 8 seconds), or no connection. The page then hangs up, so nothing the
  server says later opens a table, and starts the game with the reference engine
  (`startSoloOnDevice`). A game the server started is never continued on the device.
- **At the table** a solo game says "Saved" next to the round, draws no ring on the player, and a
  lost connection says the game waits and no card is played (`TableOverlay`). The device game says
  "Offline" and that it is not counted. The renderer marks a device game with one player that way
  wherever the page sets solo up itself (`TavernHooks.soloAgain`), so the parity tests, which mount
  the renderer alone, see the legacy markup.
- **Leaving** asks first, in solo's own words. The server answers `game.leave` on a solo table with
  `ok` and nothing after it, so `RemoteTable` ends the table on that `ok`. The page then says "You
  left this game." in the table's place.
- **The ends:** a game the server finished says "Saved to your stats", a device game says it is
  not counted, and "Play again" leads to the setup, not to the last crew.
- **The mock** plays solo by the same rules (`src/net/mock/server.ts`): the refusals, the table
  that stands still while the player has no socket, the leave that is `ok` alone, and one
  unfinished solo game per player.
- The last setup is kept on the device (`skullking-tavern.solo.v1`), as a convenience.

## The tables

The index, the ranked page and the tables of friends and the public ones are drawn as
`design/skt.pen` draws them (plan item W4): one column on a phone, three from 1000 px where a page
has that much to show. They are pages of the frame (`Page` and `Bar` in `src/online/parts.tsx`),
with Skull King's bar. A wide window has the sound settings and the player in it. The queue, the
code, the ladder and the profile are the screens they were.

- **`/skull-king/online`** is three doors. "Quick play" sends `queue.join` with `casual`. "Public
  tables" and "Your table" are links to their pages. "Join with a code" is under them.
- **`/skull-king/ranked`** is one door: "Find a ranked game" sends `queue.join` with `ranked`, and
  nothing else. There are no rules to pick. The page lists the rules the server says it plays
  (`ServerConfig.standard`), the season (`ServerConfig.season`) and the seven tiers. A guest reads
  "Ranked needs a free account." and cannot join. An account whose `Me.cooldownUntil` is ahead of
  the server's clock reads "Ranked is closed for you." and cannot join. No time is drawn: the page
  only looks again when that time has come (`src/online/ahead.ts`).
- **A new table** (`SettingsForm.tsx`) is the solo setup's cards: the five lengths, the two
  scorings and the four extras (`src/skullking/rulesets.ts`). It has no control for the seats, the
  pace or the bots' skill, and always sends `maxPlayers: 4`, `pace: 'standard'` and
  `botLevel: 'normal'` (`FIXED` in `settings.ts`), whatever the device remembers. "Seat bots" is on
  as the page opens. On, `lobby.create` leaves `allowBots` out. Off, it sends `allowBots: false`.
  The host's "Table rules" is the same form without the pill and the switch: no message changes
  who can join or whether bots are seated, and the seats, pace and skill stay what the table has.
- **A waiting table** (`LobbyRoom.tsx`) shows the code of a private table and none of a public one.
  "Add a bot" and the mark that removes a bot are the host's, and only at a table whose
  `Lobby.allowBots` is not `false`. Start is enabled when two people are seated and every person
  is ready. That is for feedback: the server decides.
- **The public list** (`PublicTables.tsx`) is `GET /lobbies` as it came. A row with `hostColor` is
  "{hostName}'s table". A row without one is the name the server sent and nothing else. Each row
  says how many seats are taken, the length of the game, and "Bots" or "No bots" (`allowBots`
  left out means bots).

Whether a table seats bots is the server's to keep. The page draws what `Lobby` and `LobbySummary`
say, and remembers nothing of the switch itself. A server that drops `allowBots` therefore gets a
table that seats bots, and the page says so.

## Online

`docs/protocol.md` is the contract, and the server is the only authority
(`docs/agent-rules/server-authority.md`). Nothing below decides anything about a game.

- **`SocketClient`** (`src/net/socket.ts`) opens the socket, says `hello`, takes `ok` then `welcome`,
  and keeps the server's clock from `welcome` and from every `ping` (`serverNow()`). `request()`
  answers every message with exactly one result and never rejects. A dropped connection is retried
  after 0.5 s, 1 s, 2 s and so on up to 15 s, with jitter. Every request still waiting on the closed
  socket is answered `OFFLINE` and forgotten: nothing is sent a second time, and the `welcome` of the
  next socket replaces what was known. `superseded` and `PROTOCOL_UNSUPPORTED` end the connection
  without a retry. Listeners get every reply and push synchronously, in the order of the frames.
- **`Api`** (`src/net/api.ts`) is REST under `/api/v1`: register, login, logout, the profile, another
  player's profile, the public lobby list, the ladder and the server config. Every call ends in a result with
  the server's error code, or `OFFLINE` when there was no answer. Nothing keeps a password or a
  token after the call that carried it.
- **`Online`** (`src/net/online.ts`) is what the page knows about its session: the link, `me`, the
  lobby, the queue, the open table, and a notice when something ended while the player was not
  looking. The screens read it with `useSyncExternalStore`. Its intents only ask. Registering and
  saving the profile keep the session and take `Me` from the answer; a login connects again with the
  new session, and a logout hangs up.
- **`RemoteTable`** (`src/table/remoteTable.ts`) implements `Table` for the one seat `game.start`
  calls `me`. `dispatch` sends `game.bid`, `game.play` or `game.ability` with the round and trick on
  screen and no seat; `advance` is `game.ready`. It tells the renderer which update gives the input
  back (`UpdateInfo.unlock`): the one that follows the `ok`, and no other seat's. The update that
  answers `game.leave` is the last (`UpdateInfo.last`), and the table comes down when it has been shown.
  Every view carries what the server says about the table (`TableView.online`): each seat's status,
  who is ready for the next round, and the deadline the table is waiting on.
- **At the table** the renderer draws that: a ring around each avatar the deadline names, emptying
  until `deadline.at` on the server's clock (`deadlineRing` in `views.ts`; a CSS animation from what
  is left, so nothing redraws it); a tag on a seat whose player is offline, away or replaced by a
  bot; "Ready · waiting for 1 more" after this seat's `game.ready`; and a line when the server
  played for a seat whose time ran out. The page only shows the clock. The move at its end is the
  server's. A deadline only says when it ends: how long its clock runs in all is known when the
  step that started it arrives, and a clock met while it runs (after a reconnect) is taken to be a
  standard one (`src/net/timing.ts`).
- **A lost connection** at the table puts a card over it (`src/online/TableOverlay.tsx`) and makes
  the table underneath inert until the next `welcome` has replaced what it shows.
- **A reload** connects by itself when the last page on the device was seated in a lobby or at a
  table (`OnlineMemory`, in localStorage as `skullking-tavern.online.v1`). Where it lands is what
  `welcome` says: the table at its snapshot, the lobby, or the hub. A `game.over` that follows a
  `welcome` without a game is shown as a notice and opens no table. Whose seat the result is about
  is in the message (`game.over.seat`); the seat the device remembers is used only when it is not.
- **The mock server** (`src/net/mock/server.ts`) speaks the same messages inside the page, for the
  tests and for `?mock` in a development build (it is not in the production bundle). It runs
  accepted play through the reference engine, one step at a time, and sends each seat its own view.
  It has private and public lobbies, bot seats, tables that seat no bots (`allowBots: false` is
  kept, and `lobby.addBot` there is `BOTS_DISABLED`), the deadlines of §5.6, accounts (register, login,
  logout, profile), the public lobby list, the casual queue with bot fill, and stats after a game.
  It has a ranked queue, a rating change after a ranked game, a cooldown after a ranked leave and a
  ladder, following the rules of `docs/protocol.md`: the tier bands, placement until the fifth
  game, the cooldown that doubles, the season that is the UTC quarter. It does not rate: where the
  server runs Weng-Lin the mock moves a rating by a fixed step per place, and it seats the first
  four in the ranked queue with no skill window. It has no emotes and no away detection. It does
  close a dropped seat after two missed turns in a row. Every page has a mock of its own: two tabs
  cannot meet in one lobby or one queue, so a ranked table never forms under `?mock`, and a lobby
  never starts there either: it needs two people, and a bot is not one of them. Casual quick play,
  which fills the open seats with bots, is the way to a table under `?mock`. Behind `?mock` it keeps its
  state in sessionStorage and comes back with it after a reload, with every seat offline, as a
  server would find them.
- The real backend (`src/net/transport.ts`) asks `POST /api/v1/auth/guest` for a session once,
  opens `/api/v1/ws` on the same origin, and sends REST with the same cookie.

The browser test of four players (plan item C8) is `e2e/four-players.e2e.ts`. It plays against the
mock host until the Rust server answers on 127.0.0.1:8080, and against that server from then on,
with no change to the script (`e2e/README.md`).

## What keeps the port honest

- `src/game/engine.fixtures.test.ts` replays every game in `fixtures/engine/`. The Rust engine
  replays the same files.
- `src/game/reference.test.ts` runs the legacy engine next to this one: the seeded shuffle, whole
  bot games decision by decision, and the scorekeeper's scoring.
- `src/tableview/parity/` runs the legacy page's own script next to the lifted renderer and compares
  markup, storage, animation calls, Web Audio calls and vibration step by step, through a solo game,
  pass-and-play, the scorekeeper and every sound. The test page loads no recorded takes, so what is
  compared is the synthesiser.

The legacy file is the reference for all three. It changes only when the rules change on purpose,
together with the pinned hash in the fixture generator.

## Deliberate differences from the legacy page

- No `window.SKT`. Tests import the modules.
- Fonts are bundled (`@fontsource`), not loaded from Google.
- The renderer can be taken off the page again: `mountTavern()` returns a cleanup that removes every
  listener, timer, banner and the sprite. State is read from storage at mount, not at import.
- A seat colour is put into a `style` attribute only if it is a six-digit hex value (`cssColor`).
- The prefixed `webkitAudioContext` of Safari before 14.1 is not used.
- A played card and a plain button press sound recorded takes ([Recorded sounds](#recorded-sounds)).
  The legacy page synthesised them. Those recipes are still there: each plays until its takes are
  loaded, and for good if they cannot be.
- The home screen has music ([Menu music](#menu-music)). The legacy page had none. It follows the
  "Sound effects" switch and the volume slider; there is no control of its own.
- States the legacy code could not reach but would have crashed on (no pending ability, no last
  trick) render nothing instead.
- The bid at the table is a slider on a sheet that rises from the bottom edge (`bidSheet` in
  `views.ts`, driven in `events.ts`), where the legacy page has a row of chips. It is the first
  screen drawn differently on purpose. The parity harness compares the two bid controls on what
  they offer and what their button says (`pageHtml` in `parity/harness.ts`) and everything around
  them as markup, as before. The scorekeeper still uses chips: it sets a bid for every player on
  one screen.
- The table says which seats are played on this device (`Table.localSeats`). The legacy page took
  every seat without the `bot` flag for one, which is true offline and wrong the moment another
  human plays from somewhere else. `LocalTable` is still handed every human seat, so solo and
  pass-and-play are as they were; the renderer no longer reads the flag for it (`localSeatsOf`,
  `localActor` in `state.ts`).
- `Table.dispatch` answers with a promise. `LocalTable` resolves it before `dispatch` returns, so
  offline nothing waits. The renderer sends through `dispatchWithin`, which gives up after 8
  seconds. A refused or unanswered action unlocks the input and puts back what the player had
  picked (the card, the bid, the Smuggler's discards); the legacy page dropped the pick.

## Recorded sounds

`src/sound/samples/` holds the takes, `src/sound/samples.ts` fetches them at startup, and
`Sound.samples()` hands them to the mixer, which decodes them at once (with an offline context, so
it does not have to wait for the first tap). A sound with takes plays one of them, never the one it
played last, a little faster or slower each time. `src/sound/sound.test.ts` covers that and the
fallback to the recipe.

| Sound      | Takes                                  | Speed drift | Made from the prompt                                                                                               |
| ---------- | -------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------ |
| `cardPlay` | `card-play-a.wav` to `card-play-d.wav` | up to 6 %   | "Single playing card slapped down onto a wooden table, crisp papery snap with a soft woody thud, close-mic, dry"   |
| `tap`      | `tap-a.wav` to `tap-c.wav`             | up to 4 %   | "Single soft wooden button click, short dry tap of a fingertip on a small wooden box, warm and rounded, close-mic" |

- All of them were generated on 2026-10-11 with ElevenLabs Sound Effects v2
  (`eleven_text_to_sound_v2`): one hit from each variation it made for the prompt, left out where
  the variation did not hold a clean one. Using them is subject to the ElevenLabs plan they were
  generated under.
- Each was cut to the hit, faded in and out, and stored as 16-bit mono WAV at 44.1 kHz: every
  browser decodes it and it starts on the first sample. The card takes are 0.19 to 0.24 s long with
  the slap 35 to 50 ms in. The tap takes are 0.10 to 0.12 s long with the tap 6 ms in, because a
  button has to answer at once.
- Each is stored so that its loudest 60 ms has an RMS of 0.05. `TAKES` in `sound.ts` then sets the
  level: the synthesised `cardPlay` recipe renders about 0.058 there, so the card takes play at a
  gain of 1; the `tap` recipe renders 0.038 on its bus of 2.4, so the tap takes play at 0.32.

- The home screen has a second button, "Play online", next to "Play" (`.play-row`). The parity
  harness compares the button both builds share (`pageHtml`).
- The table can be an online one. Then the X asks before it gives the seat to a bot, the end screen
  has one button (back to the lobby), and neither the stats nor the saved offline game are touched.
- A table says which update gives the input back (`UpdateInfo` in `table.ts`). `LocalTable` says
  nothing, so offline every update still does, as below.

## Menu music

`src/sound/music/` holds the tunes, `tavern.mp3` and `tavern-b.mp3`. `src/sound/music.ts` lists
them with the place of each one's loop (`TUNES`), fetches them at startup and hands the ones that
came to the mixer together (`Sound.tunes()`). The renderer asks for the music with `Sound.music()`
on every redraw (`tuneMenu` in `tableview/render.ts`). On a real browser the home
screen opens under a "Welcome back" sheet. Come in closes it and starts the
theme. It keeps playing through setup and the online screens, and stops when a
game is on screen. The end screen stays quiet. Back on the home screen it
starts again. A background tab pauses it. "Sound effects" off silences it; the volume slider moves it with
everything else. The synthesiser has no recipe for it: a tune that cannot be fetched or decoded is
left out, and with none the menu is quiet. `sound.test.ts`, `music.test.ts`, `tavern.test.ts` and
`OnlineScreens.test.tsx` cover it.

One tune plays at a time, round its own loop and from the top. The first is drawn at random each
time the page loads. Every time the music starts again (back on the home screen, back in the tab,
sound back on) it is the next tune's turn, so a player who stays on the home screen hears one tune
go round. A third tune is a file in `music/` and a line in `TUNES`.

`tavern.mp3`:

- Generated on 2026-10-11 with ElevenLabs Music v2.5 (`eleven_music_v2_5`), instrumental, 90 s,
  from the prompt "Instrumental pirate tavern folk tune for a game main menu, warm and inviting with
  a sly, adventurous swagger. Lead fiddle melody over accordion chords, plucked acoustic guitar and
  upright bass, with a soft bodhrán and light tambourine pulse; mid-tempo around 100 BPM in a
  lilting 6/8, D minor. Steady, even energy from start to finish with no big intro, no build-up, no
  breakdown and no fade-out, so it loops seamlessly: the final bar leads straight back into the
  opening phrase. Close, natural acoustic production, no vocals, no crowd noise, no sound effects."
  Using it is subject to the ElevenLabs plan it was generated under.
- The take holds nine 8-bar phrases at 100 beats a minute (9.6 s each) and a closing chord. The
  ninth phrase is the first one again, so the loop is the first eight: from 0.030 s, just before the
  first downbeat, to 76.838 s, just before the ninth phrase's. That is 76.808 s. Over its first
  12 ms the loop fades from what the take played after 76.838 s into its own downbeat, so the notes
  still ringing at the end of the loop do not stop dead.
- It is an MP3 (48 kHz stereo, 128 kbit/s, 1.2 MB) because 77 s of stereo is 15 MB as WAV. Some
  decoders leave the silence MP3 encoding adds at the front of the file and some remove it, so the
  loop is not tied to the file's first sample: the file is the last 0.5 s of the loop, the loop, and
  its first 0.5 s again. Any stretch of 76.808 s inside it joins up with itself, wherever the
  decoder put the start. The mixer loops from 0.25 s to 77.058 s and starts playing at 0.5 s, the
  downbeat. `music.test.ts` holds the file to that length.
- It is stored at -16 LUFS (the take, 3 dB down) and plays at a gain of 0.3 (`MUSIC_V` in
  `sound.ts`): about as loud as a button tap. Decoded a tune takes about 30 MB, so it is decoded
  when it is about to play, not when it is fetched. The mixer keeps the next tune decoded while
  one is playing, so leaving a game starts that next tune in the tap. A tune started later, once
  the tap is over, is thrown away on a phone. The one that is playing holds its own buffer until
  it fades out, so two decoded tunes exist only while one is taking over from the other.

`tavern-b.mp3` is the same band in the same key, metre and tempo as the first, with a new melody:

- Generated on 2026-10-12 with ElevenLabs Music v2.5 (`eleven_music_v2_5`), instrumental, 90 s,
  from the prompt "Instrumental pirate tavern folk tune for a game main menu, a companion piece to a
  fiddle-led tavern jig: the same band and the same room, a new melody. Warm and inviting with a
  sly, adventurous swagger, a touch more wistful and seafaring. Tin whistle and fiddle share the
  lead melody, trading phrases, over accordion chords, plucked acoustic guitar, mandolin and upright
  bass, with a soft bodhrán and light tambourine pulse; mid-tempo around 100 BPM in a lilting 6/8,
  D minor. Steady, even energy from start to finish with no big intro, no build-up, no breakdown and
  no fade-out, so it loops seamlessly: the final bar leads straight back into the opening phrase.
  Close, natural acoustic production, no vocals, no crowd noise, no sound effects." It is the third
  of the four variations the prompt gave, the one the owner picked by ear. Using it is subject to the
  ElevenLabs plan it was generated under.
- The take starts on its first downbeat, holds nine 8-bar phrases at 100 beats a minute and comes
  round to its opening after 76.800 s. The loop is that long and begins there, at the ninth phrase.
  For its first 6.547 s it is the take's second pass; then it crosses over 12 ms into the first
  pass, at a quiet spot just before a note, where the two passes sound most alike. Its end, the
  take just before 76.800 s, runs straight into its beginning.
- It is stored like the first: the last 0.5 s of the loop, the loop, and its first 0.5 s again, as
  MP3 (48 kHz stereo, 128 kbit/s, 1.2 MB), at the loudness the first measures (-16.4 LUFS, the take
  3.2 dB down).

The service worker keeps every built file, so each tune adds its 1.2 MB to what an install fetches.

## Carried over as it was, to fix on purpose later

These are behaviors of the legacy page that look like bugs. They were ported unchanged so the lift
stays a lift; each fix should come with its own test.

- A table update that is waiting on a banner continues after its table was replaced: starting a new
  game within about a second can briefly show the old one.
- An error thrown while an update is presented is only logged, and can leave game input locked.
- Offline, any table update that is presented unlocks the input, not only the answer to the action
  that locked it. There the two are the same update. Online the table says which one it is.
- A refused or unanswered action is not explained to the player: the input comes back and nothing
  else is shown. Offline the page is built to offer only what the engine takes.
- During the 190 ms closing animation of a sheet, a table update can re-render it; the action then
  runs against a stale element.
- "No saved game" and "no scoresheet" are stored as the string `null` instead of removing the key.
- The one-time swipe hint is marked as shown inside a view function, so an early re-render drops it.
- Escape closes a sheet without the closing animation or sound.
- `tavern.css` still carries the legacy's literal colours next to the tokens. New code uses tokens
  only; the old rules move over as their screens are touched.
